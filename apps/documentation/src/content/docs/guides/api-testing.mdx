## The rule: test the routes, and the complex logic

Two kinds of tests are worth writing. Keep them few: one test per behaviour, not one per line or per branch. Coverage is not a goal.

**1. The routes, end to end (`*.e2e-spec.ts`).** Test the API through its routes:

- The contract of a route: status code, response shape, and the rejection of invalid input.
- Who may call it: anonymous, logged in, wrong user, wrong role.
- The business error cases the service decides, such as a conflict or a forbidden state.

**2. Complex business logic, as unit tests (`*.spec.ts`).** A pure function with many cases, such as a calculator or a parser, gets unit tests. Covering every case through the routes would cost more than testing the function directly.

**Do not write:**

- A unit test of a service, mapper, controller, guard or processor that its routes already cover.
- A test for a one-off script, such as an import or a backfill. A one-off script needs no test and no service.
- A test that only checks types, a schema shape or a mapping. The compiler and the contract already do that.
- A second test that asserts what an existing test already asserts.

## Launching tests

Run every test:

```bash
pnpm test
```

Run only the tests that your branch can affect:

```bash
pnpm test:changed
```

`test:changed` compares your branch with `origin/main`, committed or not, and runs the tests that import a changed file.
A change to a file that every test depends on runs the whole suite instead: the test setup and helpers, an entity, the database module, the Vitest config, the API's `tsconfig.json`, a `package.json` or the lockfile.
If nothing your tests import has changed, it runs no test.
It needs an up-to-date `origin/main`: run `git fetch origin main` first if your clone is old.

Run the tests in watch mode:

```bash
cd apps/api && pnpm test:watch
```

### When to run what

- While you work, run `pnpm test:changed`. It keeps each run short.
- Before you open a pull request, or before you call it ready to merge, run `pnpm test` once.
- The CI always runs every test.

:::note
If you want to know more about testing in NestJS, you can read the [NestJS testing documentation](https://docs.nestjs.com/fundamentals/testing).
:::

## Infrastructure setup

We use Testcontainers to run the infrastructure the tests need, mainly the database.

One PostgreSQL container serves the whole test run. `src/test/setup/test.global-setup.ts` starts it once, before any test file loads. The container keeps its data in memory and runs without durability (`fsync`, `synchronous_commit` and `full_page_writes` are off). The data only has to live as long as the run, so this is safe, and it makes each write much faster.

The global setup then builds a template database once, with `orm.schema.refresh()`. You don't have to do anything when you add an entity: the template is rebuilt from the entities on every run.

Each e2e test starts from empty tables:

- Each Vitest worker copies the template once, with `CREATE DATABASE … TEMPLATE`, into its own database (`test_worker_<n>`). A worker runs its tests one at a time, so no two tests share a database at the same moment.
- `src/test/setup/test.e2e-setup.ts` calls `createTestOrm` before each test. It deletes every row of the worker's database, which is faster than copying the template again.
- After each test, `cleanupTestOrm` closes the ORM. The database stays for the worker's next test.
- The e2e project sets `isolate: false`: a worker keeps the app modules loaded from one test file to the next. Don't leave a `vi.mock`, fake timers or a changed `process.env` behind in an e2e file: the next file in the same worker would see it.

A test file only has to start its NestJS app on the test's ORM:

```typescript
beforeEach(async (context) => {
  const { orm, app } = await initializeTestApp(
    { orm: context.orm },
    {
      imports: [PostModule],
    },
  )
  context.app = app
  context.em = orm.em.fork()
  context.request = createRequest(app)
})
```

The `src/test/README.md` file has the full layout of the test helpers.

## Service mocking

You can mock some services or external services by using the `vi.mock` function.

Here is an example of mocking the `EmailService` in the `test/test.e2e-setup.ts` file.

```typescript
vi.mock('../modules/email/email.service', () => ({
  EmailService: vi.fn().mockImplementation(() => ({
    sendEmail: vi.fn(),
  })),
}))

// Mocking the ai service example
vi.mock('ai', () => ({
  generateObject: vi
    .fn()
    .mockResolvedValue({ object: { analysisResult: 'mocked result' } } as never),
}))

// Mock langfuse at module level
vi.mock('langfuse', () => ({
  __esModule: true,
  default: vi.fn().mockImplementation(() => ({
    trace: vi.fn().mockReturnValue({
      span: vi.fn().mockReturnValue({
        end: vi.fn(),
      }),
      update: vi.fn(),
      getTraceUrl: vi.fn(),
    }),
    shutdown: vi.fn(),
  })),
  observeOpenAI: vi.fn((openaiInstance: unknown) => openaiInstance),
}))
```

## Utils and configurations

The `test/test.utils.ts` file contains some useful utilities for testing, like initializing the test application, creating a test user, and initializing the request with authentication.

The `vi.config.ts` file contains the vi configuration for the project. You can customize it to your needs.
