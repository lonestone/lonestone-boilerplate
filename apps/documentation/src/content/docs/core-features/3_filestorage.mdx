# File Storage

The API includes provider-neutral S3 infrastructure. Posts demonstrate how a domain module stores
an optional image. Storage is disabled by default, so an unavailable S3 service cannot prevent an
application that does not use files from starting. File operations return `503 Service Unavailable`
while storage is disabled.

`StorageModule` is infrastructure-only. It exports `StorageService`, uses one default bucket, and
does not expose HTTP routes or provider internals. It knows nothing about the database.

`MediaModule` sits next to it and owns the `Media` table. One `Media` row is one stored file: its
opaque storage key, original filename, MIME type, and size. It exports `MediaService` and
`MediaMapper`, and has no controller. Business modules own their HTTP contracts, authorization
rules, and the relation that points to a `Media` row.

## Configuration

Configure the API with these provider-neutral variables:

- `STORAGE_ENABLED`: enable the configured storage provider. Defaults to `false`.
- `STORAGE_BUCKET`: default bucket name.
- `STORAGE_ENDPOINT`: S3 endpoint. Use the provider endpoint in production.
- `STORAGE_REGION`: S3 region.
- `STORAGE_ACCESS_KEY_ID` and `STORAGE_SECRET_ACCESS_KEY`: provider credentials.
- `STORAGE_FORCE_PATH_STYLE`: required by many self-hosted S3-compatible services.
- `STORAGE_CREATE_BUCKET`: create the default bucket during startup when storage is enabled and the
  bucket is missing.

## Local RustFS

Docker Compose provides RustFS as the local S3-compatible service. Its data is stored in the
`rustfs_data` volume.

```bash
pnpm docker:up
```

The default S3 endpoint is `http://localhost:9000`. The RustFS console is available at
`http://localhost:9001`. Credentials come from the root `.env` file and are mapped to RustFS by
Compose.

## Use from API code

Import `MediaModule` in a business module and inject `MediaService`. Business modules should
depend on it instead of importing `StorageService`, the AWS SDK, or the S3 provider.

Point to the file with a relation to `Media` rather than copying its columns onto the business
entity. A `OneToOne` relation guarantees that one `Media` row belongs to a single owner:

```typescript
@OneToOne(() => Media, { owner: true, nullable: true, fieldName: 'coverImageId' })
coverImage?: Media
```

`MediaService.create` uploads the bytes and persists a `Media` entity without flushing. Attach it
to your entity and flush once, so both rows are written in the same transaction:

```typescript
@Injectable()
export class PostService {
  constructor(
    private readonly em: EntityManager,
    private readonly mediaService: MediaService,
  ) {}

  async setCover(post: Post, upload: StorageUpload): Promise<void> {
    const media = await this.mediaService.create(upload)
    try {
      post.coverImage = media
      await this.em.flush()
    } catch (error: unknown) {
      await this.mediaService.deleteObject(media.storageKey)
      throw error
    }
  }
}
```

Map the relation with `MediaMapper.toMedia` and reuse `mediaSchema` in your contracts. The storage
key is never part of the contract. The Posts example shows this pattern.

## Posts example

Set `STORAGE_ENABLED=true` so `PostModule` can upload images. Creating or updating a post uses
`multipart/form-data`: `title` as text, `content` and `tags` as JSON fields, and an optional
`coverImage` file. Omitting `coverImage` on update keeps the current file. `DELETE /api/admin/posts/:id/cover-image`
removes it. The owner can download a draft from `GET /api/admin/posts/:id/cover-image`. Published posts
serve the same file from `GET /api/public/posts/:slug/cover-image`. The domain limits cover images
to 10 MiB.

The `Post` entity points to its cover image through a nullable `coverImage` relation to `Media`,
stored as the unique `coverImageId` column. Post contracts expose the image as a `MediaSchema`:
`id`, filename, MIME type, and size. Every owner download and delete includes the authenticated
user in the query. A different user receives `404`. If SQL persistence fails after upload, the
service deletes the new object. On replace or remove, the old `Media` row is deleted in the same
flush as the post change, and its object is deleted only after that commit.

The generated SDK builds `FormData` for create and update, and returns a `Blob` for downloads:

```typescript
const created = await postControllerCreatePost({
  body: { title, content, coverImage: file },
})

const download = await publicPostControllerDownloadPublicPostImage({
  path: { slug: created.data.slug },
})
```

Keep storage mechanics in `StorageService` and file records in `MediaService`, but put access rules
and routes in the domain module.

## Production

Use a dedicated bucket and restricted credentials. Disable automatic bucket creation after
provisioning infrastructure. Configure the provider endpoint, region, TLS, retention, backups,
and lifecycle rules according to the chosen service. Domain modules should set upload size limits
that also match reverse proxy and platform limits.

AWS S3 normally uses virtual-hosted addressing, so set `STORAGE_FORCE_PATH_STYLE=false`. Keep it
enabled only when the selected compatible provider requires it.

## Remove storage

If you do not need files, leave `STORAGE_ENABLED=false` and ignore the image fields on posts. To
remove the infrastructure, remove the `coverImage` relation from posts, delete
`apps/api/src/modules/media` and `apps/api/src/modules/storage`, create a migration that drops the
`media` table, then remove the AWS SDK, direct
`testcontainers`, and Multer type dependencies if nothing else uses them. Remove the `STORAGE_*`
variables, the RustFS Compose service and volume, then regenerate the OpenAPI client.
