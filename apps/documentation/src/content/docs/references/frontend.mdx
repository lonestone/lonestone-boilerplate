# Front-end Guidelines

## Stack

See [Tech stack page](/lonestone-boilerplate/explanations/1_architecture) for the full tech stack.

## General Instructions

In general, respect the current project structure and file names.

If not specified otherwise, follow the following guidelines:

- Use kebab-case for file names.
- Use features folder to add route components or scoped components. Look at other features in the repo. It shoud look like this:
  - features/
    - common/ for common files, hooks, etc.
      - hooks/
      - utils/
      - atoms/
    - featureName/
      - components/
        - feature-component.tsx
        - another-component.tsx
      - hooks/ for hooks scoped to this feature
      - utils/ for utils scoped to this feature
- Use app folder to had global components that are used in multiple features.
- Use utils folder to had utility functions.
- Use components from @boilerstone/ui in ./packages/ui.
- Check types, schemas and sdk from @boilerstone/openapi-generator in ./packages/openapi-generator.
  - ./packages/openapi-generator/client/sdk.gen.ts
  - ./packages/openapi-generator/client/zod.gen.ts
  - ./packages/openapi-generator/client/types.gen.ts
- Use shadcn/ui for components.
- Use react-router for routing.
  - routes are usually defined in a `routes.ts` file
- Compose screens. Do not copy a header into a new page.
  - A route layout writes the frame once: header, main, footer. Brand, navigation, theme, and auth stay in that file. A signed-in app uses `AppLayout`. Do not add a shell that takes those blocks as props.
  - A screen composes `Page` and `PageHeader`. `band` is the public title. `inset` is the title row inside the dashboard. Eyebrow, title, and description are the text. Anything else is a slot: `before`, `leading`, `actions`.
  - A block inside a screen composes `Section` and `SectionHeader`. The comments list under an article is the reference. It is not a page.
  - A paged list composes `Pagination`, `PaginationContent`, `PaginationItem`, `PaginationPrevious`, and `PaginationNext`. The page keeps the page number, the range, and the labels.
- Use react-hook-form for form handling.
- Use zod for form validation.
- Use @boilerstone/i18n for internationalization, no hardcoded strings.
- Use tanstack-query for data fetching. The [data fetching guide](/lonestone-boilerplate/guides/data-fetching) explains why; the rules are:
  - one hook file per feature, `/features/feature-name/hooks/use-feature-name.ts`, with a key factory and one hook per query and per mutation (`useUserPost`, `useUpdateUserPost`). The hooks call the generated SDK. There is no separate queries file.
  - components call the hooks. No SDK call and no inline `queryKey` in a component body. Route loaders may call the SDK. Better Auth (`authClient`) calls are out of scope.
  - keys come only from the feature's key factory, from broad to specific (`all`, `lists()`, `list(params)`, `detail(id)`). Every value the `queryFn` reads goes in the key. Another feature that must invalidate yours imports the factory.
  - `throwOnError: true` on every SDK call inside a `queryFn` or `mutationFn`. Never set it globally, and never write `if (response.error) throw`.
  - mutation hooks use `useQueryClient()`, never the `queryClient` singleton, and only handle the cache. They return the invalidation promise, so `isPending` covers the refetch.
  - no toast, navigation or `console.error` inside a hook. The component passes them to `mutate(variables, { onSuccess, onError })`.
  - reference implementations: `apps/web-spa/app/features/examples/user-posts` (queries and mutations) and `apps/web-ssr/app/features/comments` (infinite query)
